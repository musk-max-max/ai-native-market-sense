## 2) 实际超时配置（可直接复核）
services 内所有 Pool 构造（含 services/market/src/plugin.ts:97）均为:
  new Pool({ connectionString: config.databaseUrl })
即未传 connectionTimeoutMillis / query_timeout / statement_timeout。
DB 端（a13_verify，默认库配置，角色无 rolconfig）:
  SHOW statement_timeout                    -> 0        (无限制)
  SHOW idle_in_transaction_session_timeout  -> 0
  SHOW lock_timeout                         -> 0
  select rolconfig from pg_roles where rolname in ('market_app','warehouse_loader','ci_deploy_writer')
    -> 全部为空
结论（配置事实，不是测量值）:
- connect_timeout: 未配置。node-postgres 默认 connectionTimeoutMillis=0（不超时），
  由 OS TCP 超时兜底（本机不可控，量级 ~75s），远超 #2 的 1500ms。
- statement_timeout: 未配置（DB 0 + 客户端无 query_timeout），查询可无限挂起。

## 3) 这对 #2/#3 的直接影响（推理，待 DROP 环境实测确认）
EntitlementGate.evaluate() 只是 `await this.repo.fetchControl()`，没有 Promise.race/超时；
failures/熔断只在 promise reject 时累加（entitlement-gate.ts:157-161）。
黑hole 下 promise 不 reject -> 请求挂住：
- 20 样本 P95 ≤1500ms：不可能成立（首个请求就会 >1500ms，甚至 > OS 超时）；
- 熔断后 P95 ≤50ms：熔断根本不会被触发（没有 reject 可计数），该数字不存在。
=> 必须先补超时（连接 + 查询 + 读 control 的请求级超时），否则 #4 即使有 DROP 也是红。

## 4) 待办/建议（不改他人代码，交给 A3/H4 定）
1. Pool: connectionTimeoutMillis=1000、query_timeout=1000（或 statement_timeout=1s 服务端），
   并在 EntitlementGate 对 control 读加 AbortSignal/超时，超时即 reject 走 5s 负缓存/熔断。
2. 有 DROP 能力的环境（Linux runner + iptables 或带 NET_ADMIN 的容器）上重跑：
   iptables -I OUTPUT -p tcp -d 127.0.0.1 --dport 55432 -j DROP
   记录 20 样本、熔断后 P95、撤规则恢复时间、/healthz reason 与响应体不含 DSN/主机/端口。
3. 本文只作为"无法构造 + 阻塞性配置缺口"的证据，不计入 #4 PASS。
