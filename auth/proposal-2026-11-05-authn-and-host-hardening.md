## 2. 主机威胁模型（H5 要求写清）

| 要素 | 内容 |
|---|---|
| 资产 | 行情数据（`serving.serving_quote_latest`、`dwd_stock_bar_daily` 等）、tushare 凭证、SSH 私钥、部署凭证、主机 root |
| 信任边界 | **API/Web（应用边界）** ← 403/tier 门禁只在此生效；**主机（root/docker）** ← 数据面实际控制者；**云 SG** ← 用户控制面 |
| 主要 actor | ① 公网扫描/爆破者；② 有主机 shell 的熟人；③ 内网隧道使用者（可二次转发）；④ 误操作/临时调试的人（留下 `ms-nginx` 这类残留） |
| 已知边界（必须写进威胁模型，不得写成「有控制」） | **授权只在 API 层**：root/docker 可 `docker exec postgres psql` 直读数据，完全绕过 403/tier（SEC-004，artifact L47–L51）。`docker.sock=root:docker 660`、docker 组当前无成员、无 uid≥1000 可登录用户 → 现状只有 root；**给任何熟人 shell/docker 组，C 端门禁对数据面整体失效** |
| 由威胁模型推出的硬约束 | a) 主机管理面必须默认拒绝、最小暴露（否则一条弱口令=数据面全穿）；b) 主机访问者必须具备**可区分身份**，否则无法证明「仅本人查看」；c) 任何 0.0.0.0 绑定都必须被检测 |

## 3. 身份架构：三入口一判定点（决策 #5）与当前事实

当前事实（A19 实测）：**运行栈本身无用户认证** —— web 匿名 200；`E2E_AUTH_TOKEN` 为空，dev-token 仍 401；
Basic Auth 只存在于已停的 `ms-nginx`；当前靠 `internal_eval` 的 403 兜底。即「内网模式下是否还需要认证」**没有技术答案**，
这是本提案第 1 个待 H5 拍板项。

| 入口 | 现状 | 目标（提案） | 判定点 |
|---|---|---|---|
| 主机管理面（SSH/docker） | 公网 22 + root 密码认证 + 1130 次爆破 | 见 §4；仅白名单来源 + 密钥/硬件因子；无共享账号 | sshd + SG/ufw |
| 内网用户面（web/api） | **无认证**（匿名 200） | 见 §3.1 三选一；每次请求可归属到人 | API 中间件（唯一判定点，服务端强制） |
| C 端 tool calling / token | `internal_eval` 403；无 token 体系 | 由 A4 权限模型定；本提案只要求：token 有主体、有期限、可吊销（基线 #1/#2） | API 中间件 |

### 3.1 内网用户面认证：三选一（**待 H5 拍板**）

| 选项 | 内容 | 优点 | 代价/风险 | A9 立场 |
|---|---|---|---|---|
| A（推荐，过渡期） | **单用户凭据 + 反向代理鉴权 + 每请求主体**：一个本人账号（口令 + TOTP 或 SSH 密钥衍生），web/api 前置统一验签；请求头携带 `sub`，API 只信反代注入的身份；匿名一律 401 | 最小改动；与 L100 ④「仅用户本人单人访问」对齐；可技术举证「谁看了什么」 | 反代是单点，须防伪造头（只监听 loopback、`trustProxy` 明确定义）；不做多人 | **推荐**：先满足「单人可举证」，再谈多人 |
| B | **员工 OIDC**（决策 #5 的员工入口） | 标准化、可吊销、审计好 | 单人/自用场景过重；引入 IdP 依赖；与 P0 范围不符 | 留作 S1+ 多人时启用 |
| C | **维持无认证**（仅靠 loopback + SSH 隧道做隐式身份） | 零改动 | **无法区分操作者**：同一 SSH 账号可隧道转发给第三人；服务端日志无身份；L100 要求的「单人凭据」不成立 → 无法举证「仅个人查看」 | **不接受**作为 go-live 状态；只可作为当前已知缺口登记（SEC-006） |

> 无论选哪个，**「默认拒绝」必须落地**：未携带有效身份的请求一律 401/403，不允许「缺省放行 + tier 兜底」。
> tier（`internal_eval`/`c_end_display`）是**授权**机制，不是**认证**机制，二者不能互相替代。

## 4. sshd 硬化规格（门禁 ⑤-1/2/3/4）

| 项 | 目标值 | 说明 | 验证（只读） |
|---|---|---|---|
| `PermitRootLogin` | `no` | root 禁止直接登录；管理用个人账号 + `sudo`（有审计） | `sshd -T \| grep -i ^permitrootlogin` |
| `PasswordAuthentication` | `no` | 关闭密码通道（A19 证明当前 `publickey,password` 均可） | `sshd -T \| grep -i ^passwordauthentication` |
| `KbdInteractiveAuthentication` | `no` | 防 PAM 交互式绕过 | `sshd -T \| grep -i kbdinteractive` |
| `MaxAuthTries` | `3` | 当前 6；配合 fail2ban | `sshd -T \| grep -i maxauthtries` |
| `AuthorizedKeysFile` / `authorized_keys` | 仅本人密钥，行数=1，逐条登记 owner/用途/指纹 | A19 实测 1 行；须留指纹台账，禁用未知 key | `wc -l ~/.ssh/authorized_keys` + `ssh-keygen -lf` |
| `AllowUsers` / `AllowGroups` | 显式白名单（如 `deploy`，不含 root） | 默认拒绝的落点 | `sshd -T \| grep -i allow` |
| fail2ban | `active`，sshd jail 启用，`maxretry=3`、`bantime` 按需（≥1h） | 替代「无防护被爆破」现状（1130 次） | `systemctl is-active fail2ban`；`fail2ban-client status sshd` |
| SG/ufw 来源 | 22 **仅白名单 CIDR**（用户固定 IP / VPN 出口） | 与 ⑤-4 一致；`Anywhere` 视为 FAIL | `ufw status verbose`；SG JSON |

**变更风险与顺序**（执行归 A13，须 H5 批准）：① 先确认个人账号 + sudo + 新密钥**已可用**；② 再关密码认证/root 登录；
③ 再启用 fail2ban；④ 最后收 SG 白名单。**每一步都保留一条已登录会话**，避免锁死；变更窗口与回滚（临时恢复旧配置 + SG 打开）
写进变更单。**不得**在未确认新通道可用前关闭密码认证。

## 5. SG / ufw 基线（门禁 ⑤-4/5）

| 层 | 目标 | 归属 | 验证 |
|---|---|---|---|
| 云安全组（控制面） | 入站默认 deny；仅 22 白名单；**无** 80/8888/20/21/888/25730/39000-40000 对 Internet 放行；出站按需 | **用户**（云控制台；A13 无云 API 凭证） | SG JSON/截图；或书面「用户负责、H5 不验」→ 记 residual，**不记 PASS** |
| ufw（主机侧） | `default deny incoming`；允许清单**仅** 22/tcp 且限来源；清理遗留面板端口 | A13 | `ufw status verbose`（`LANG=C`） |
| docker 端口映射 | 业务容器一律 `127.0.0.1:<port>`；**stopped 容器的残留 PortBindings 也要清除**（当前 `ms-nginx` 保留 `0.0.0.0:80`） | A13 | `docker inspect -f '{{json .HostConfig.PortBindings}}'` |
| 通配监听 | 仅 22（`ss -ltnp`）；出现业务端口 `0.0.0.0` = 立即按暴露处理 | A13 | `ss -ltnp` |

> 现状（A19）：80/8888 = `reachable-RST`（缺监听而非被拒）；临时绑 0.0.0.0 后外网 200（≈0.075s）→ **SG+ufw 尚未拒绝**。
> 这是「armed」状态，必改；否则任何一次调试绑定都直接公网暴露。

## 7. 审计与身份缺口（SEC-006；定性归 H3）

**事实**：无用户身份（匿名 web 200）、无访问审计（运行态 `ENTITLEMENT_AUDIT=0`、`audit.entitlement_events` 0 行）、
无按用户限流（桶按 web 容器源 IP 共享）。**因此技术上无法证明 tushare「仅个人查看」**；任一隧道持有者可在自己机器二次转发，
服务端无可观测阻断证据。

**技术侧最小要求**（不替代 H3 定性，只为「可举证」创造条件）：
1. 每个受授权接口的请求日志含 `sub`（主体）+ `route` + `status` + `as_of`，且**不可由客户端伪造**（只信反代注入，`trustProxy` 明确）；
2. 认证事件（成功/失败/注销）入审计，保留期按 H3 §2.3（留痕 3 年）与基线 #7；
3. 主机侧 SSH 登录事件入 `auth.log` 并有 fail2ban 处置记录；`sudo` 操作可追溯；
4. 检测手段（不是根治）：隧道/转发无法在服务端阻断时，至少通过「同一主体多源 IP」「异常时段」「非白名单来源」规则告警（A13/A4 落）。

**明确不做的承诺**：本提案**不声称**可以技术阻断二次转发；能否证明「仅个人查看」最终取决于 H3/tushare 书面口径与主体范围，
技术侧只提供「谁是主体、看了什么、从哪来」的证据链。
